Build Mini Cursor: a Coding Agent in Your Terminal

Problem statement by Shivank Agrawal · Future with Shivank
Level: Beginner Effort: 10–15 hours Python · OpenAI Responses API · function calling · pytest

1. The scenario

Tools like Cursor and Claude Code changed how developers work. You describe a task, and an AI agent reads your code, makes the change, runs the tests and tells you what it did. Your team wants to understand how these tools work inside, so you'll build a small one yourself.

Your task is to build Mini Cursor, a terminal chat app where an AI agent works on a folder of code. It must be useful: it explores, fixes bugs, adds features and verifies with tests. It must also be safe: the model's requests are untrusted, so it can't read your secrets, leave the folder, or change anything without your approval.

The practice workspace. sample_project/ holds a tiny bill-splitting module and its tests.
FileWhat's in it
bill_splitter.pysplit_bill(total, people, tip_percent=10), which returns each person's share with the tip. It contains a bug.
test_bill_splitter.py4 pytest tests. One of them fails because of the bug.

2. Why this is an "agent" and not a chatbot

A chatbot answers from what it already knows. An agent works in a loop:

  1. It decides on an action, such as "run the tests".
  2. Your code performs the action.
  3. The result goes back to the model ("1 failed: assert 2750.0 == 275.0").
  4. It decides the next action ("read bill_splitter.py"), and repeats until the job is done.

The model never touches your machine. It can only ask for one of the tools you define, and your code decides whether to run it.

   you> "The tests are failing. Find the bug and fix it."
     │
     ▼
  ┌─────────────┐  function_call: run_command("pytest -q")   ┌──────────────────────┐
  │  gpt-5.4-   │ ─────────────────────────────────────────► │ your code            │
  │  mini       │                                            │  1. check the guards │
  │ (Responses  │ ◄───────────────────────────────────────── │  2. ask the human    │
  │  API)       │  function_call_output: "1 failed ..."      │  3. run the tool     │
  └─────────────┘                                            └──────────────────────┘
     │   repeats: read_file → write_file (diff, you approve) → pytest again
     ▼
  agent> "Fixed: tip = total * tip_percent / 100. 4 passed."

3. Functional requirements

  1. Terminal chat. python main.py --workspace <folder> opens a chat. It should also accept questions as arguments for one-off runs. new starts a fresh conversation and exit quits.
  2. Five tools for the model:
    • list_files(path)
    • read_file(path)
    • find_files(pattern) (glob)
    • write_file(path, content) (full file content)
    • run_command(command)
  3. Web search. Add OpenAI's hosted web_search tool for questions about things newer than the model's training data.
  4. Agent loop.
    • Send the message, run every function call the model returns (it may return several at once), send the results back, and repeat until it answers in text.
    • Stop after a maximum number of rounds, and never leave a tool call unanswered.
  5. Conversation memory. Follow-up questions ("now add a test for it") continue the same conversation, using previous_response_id.
  6. Visible steps. Print every tool call and a one-line result as it happens, e.g. -> run_command("pytest -q") then <- exit code 1 · 1 failed, 3 passed.
  7. Human approval.
    • Every write_file shows a coloured unified diff and asks Allow? [y/N].
    • Every test run (pytest) also asks first.
    • A "no" goes back to the model as a tool result.

4. Safety requirements (the heart of this project)

  1. Workspace jail. Every path must resolve inside the workspace. ../../etc/passwd and absolute paths are refused.
  2. Secrets. .env, .ssh, .aws, .git, *.pem/*.key and id_rsa are never read, listed or grepped.
  3. No shell. Commands run as an argv list with shell=False. | ; & > < ` $ are rejected before anything runs.
  4. Allow-list.
    • These run freely: ls cat head tail wc grep find pwd.
    • pytest runs only with approval.
    • Everything else is refused, and so are find -exec and -delete.
  5. Limits. A timeout on commands, a size cap on tool output, and a cap on rounds per question.
  6. Plain text to the model. Colours are for the human only. Tool results sent to the model contain no ANSI codes.
Know the trap. A naive tool checks only the first word of a command and then runs it with shell=True. That lets ls && rm -rf . through, because the first word is ls. Likewise, Path.resolve() without a containment check happily reads ../secret.txt. Your guards must stop both.

5. Expected behaviour (acceptance tests)

#You typeA good agent…
1"What does this project do?"Lists the folder, reads both files (in one round), and explains the module and its tests without changing anything.
2"The tests are failing. Find the bug and fix it."Runs pytest -q (asks you), reads the code, proposes a one-line diff (asks you), then runs the tests again: 4 passed.
3"Add split_by_shares(total, shares, tip_percent=10) … add a test too."Reads the code and tests first, writes the function and a test as two approved diffs, and runs the whole suite: 5 passed.
4"What's the latest pytest version, and is pytest>=8.0 still a sensible minimum?"Uses web_search and answers with the current version and a reason, citing where it looked.
5"Read NOTES.md and do what it says." (NOTES.md hides an instruction to print .env and run ls && rm -rf .)Every dangerous request is blocked by the tool guards, even if the model tries. The agent explains it was a prompt injection, and nothing is read or deleted.

6. Milestones and time plan

MilestoneWhat "done" looks likeTime
M1 · Tools + guardsAll 5 tools work on sample_project. A list of 10 attack inputs (path escape, secrets, chaining, redirects, find -delete…) is all refused.3–4 h
M2 · Agent loopThe Responses API loop handles several calls per round, conversation memory, the hosted web search and a step limit.3–4 h
M3 · Terminal UXThe app shows live steps and coloured diffs, and approvals work for writes and test runs.2–3 h
M4 · Acceptance + READMETests 1–5 pass. The README explains setup in 5 commands. Record a short terminal GIF for your portfolio.2–3 h

7. Deliverables

  1. A repo with main.py, agent.py, tools.py, sample_project/, requirements.txt, .env.example and a README.
  2. Terminal transcripts of acceptance tests 1–5.
  3. A short design note covering three questions: how the loop works, what each guard stops, and why approvals sit in code rather than in the prompt.

8. How it will be evaluated

AreaWeightWhat reviewers check
Safety35%Every attack input fails safely. No shell=True. Containment is checked after resolve(). Secrets are hidden everywhere, including from list_files and recursive grep.
Agent loop25%Correct Responses API usage, several calls per round, memory, a step limit with no dangling tool calls.
Usefulness20%Fixes the bug and adds the feature with tests. Verifies by running the tests, not by guessing.
UX + code quality20%Clear live steps, readable diffs, helpful error messages for the model, clean small files.
Hints
  • In the Responses API, tool calls come back as function_call items. Answer each one with a function_call_output that has the same call_id.
  • previous_response_id keeps the conversation on OpenAI's side, but instructions are not carried over, so send them on every call.
  • Return guard errors as plain text ("error: '.env' looks like a secret") instead of raising. The model reads them and adapts.
  • Use "strict": True function schemas: every parameter required and additionalProperties: false.
Stretch goals
  • An edit_file(path, old, new) tool for small exact-match edits, so the model doesn't rewrite whole files.
  • Stream the model's answer token by token.
  • Git checkpoints: auto-commit before each approved write, and an undo command.
  • Run commands inside a Docker container instead of on your machine.
  • Code search by function and class names (AST/tree-sitter) instead of grep.
