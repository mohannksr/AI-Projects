Start here

One auction, eight questions

Imagine one auction. Dana is clearing out her home lab and lists a used GPU (a graphics card, the part that runs AI models) with a starting price of $100. The auction closes at 6:00 pm. Three people want it: Asha, Ben and Chen.

Asha bids $101. A minute later Ben and Chen both type $102 and click Bid in the same second. Bids keep coming until Chen bids $107 two seconds before six. Then the clock passes 6:00 pm.

That small story hides eight hard questions. Each part of the course answers one of them, and each answer adds one piece to the system:

  1. 1FoundationIs the stack alive?
  2. 2Auctions & bidsList, bid, check the rules
  3. 3The raceOnly one $102 wins
  4. 4Live updatesPages change by themselves
  5. 5Hidden defectFind the planted bug
  6. 6ClosingTell the winner, crash-proof
  7. 7CheckoutChen pays, provably
  8. 8TracingFollow one auction end to end

This page covers the setup and Part 1, then plans Part 2. Page 2 builds Parts 2–4. Page 3 ships Parts 5–8.

About the course

This project follows Build a Fullstack App with Codex by Spencer Schneidenbach on master.dev: 27 video lessons, about 4 hours 41 minutes, with a public repo holding the finished app, one folder per part. We link to each lesson at the matching step. The prompts, explanations and simulators here are our own, written so they work in any of the three big coding agents, and on Windows as well as macOS.

The big picture

The system you'll end up with

By the end, seven running pieces work together. You don't need to know any of them yet; each part introduces one, and this diagram shows where it fits.

Words you'll meet
  • API: the server program the browser talks to over HTTP. Here it's written with Fastify, a small Node.js web framework.
  • PostgreSQL: the database. It's the single source of truth: if the database says Chen won, Chen won.
  • Docker and Docker Compose: run PostgreSQL, Redis, RabbitMQ and Jaeger in containers, so you don't install them by hand.
  • Vite: the tool that serves and rebuilds the React web app while you work.
  • Playwright: a library that drives a real browser from a test, so the agent (or you) can click through the app automatically.
  • Migration: a numbered SQL file that changes the database's shape. They run in order, once each.
  • Vertical slice: a small piece of work that goes through every layer (database, API, page) and ends with something you can click.

The method

How the work is done

Every part follows the same loop. Learn it once here; the rest of the course repeats it.

An AI coding agent is a program that reads your project, runs commands in your terminal (install, test, start), edits files, and reports back. It's not autocomplete. You give it a task in plain English, and it works for minutes at a time.

That power cuts both ways. An agent that misunderstands you will happily build the wrong thing, fast, and tell you it's done. The course's answer is a set of habits:

  • Plan before code. The agent interviews you first (this is called grilling), and writes the answers down.
  • Small slices. Work is split into pieces that each end with something you can click. The agent builds one, then stops.
  • Prove, don't claim. Every slice ends with tests, a type check and a browser check that the agent actually ran.
  • Review like a colleague. You read what changed, ask for evidence, and sometimes ask a second agent to look.

How each station is laid out. From the foundation onwards, each course part is a station with the same seven blocks: 1 Goal · 2 Decisions · 3 Prompt to try · 4 What you should see · 5 View code · 6 Checkpoint · 7 Watch. The prompts are written by us and work in Codex, Claude Code or Antigravity. The code is the course author's finished version, linked to the exact lines on GitHub, so you can compare your agent's result with a known-good one.

Key lesson

Your agent's code won't match the reference line for line, and it doesn't need to. What must match are the decisions (the rules in the Decisions table) and the evidence (the checks in What you should see).

Install, macOS or Windows

macOS

  1. Install Homebrew if you don't have it (see brew.sh), then Git and nvm:
    commands
    $ xcode-select --install          # gives you git
$ brew install nvm
    Follow the lines brew prints to add nvm to your shell, then open a new terminal.
  2. Install Node 22 and make it the default:
    commands
    $ nvm install 22
$ nvm alias default 22
  3. Install Docker Desktop for Mac from docker.com and start it once. Wait until the whale icon says it's running.
  4. Install VS Code, and in VS Code run Shell Command: Install 'code' command in PATH from the command palette.
  5. Install Microsoft Edge, or let Playwright install it later.
  6. Make a folder for the course: mkdir -p ~/code && cd ~/code.

Windows (WSL2)

The course is recorded on a Mac, and the repo's commands assume a Unix shell: every npm script sets variables the Unix way (API_PORT=3101 npm run …) and calls a sh script to create databases. They won't run in PowerShell or Command Prompt. The fix is WSL2: a real Ubuntu inside Windows. Do everything in the Ubuntu terminal.

  1. Set up WSL2 with Ubuntu. Our Help page walks through it step by step. In short, in an admin PowerShell: wsl --install -d Ubuntu-24.04, restart, then open Ubuntu from the Start menu and create your Linux user.
  2. Install Docker Desktop for Windows. In Settings → General tick Use the WSL 2 based engine. In Settings → Resources → WSL integration switch on your Ubuntu distro. Apply and restart Docker Desktop.
  3. In the Ubuntu terminal, install Git, build tools and nvm, then Node 22:
    commands
    $ sudo apt update && sudo apt install -y git build-essential curl
$ curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.1/install.sh | bash
$ exec $SHELL
$ nvm install 22
$ nvm alias default 22
  4. Work inside the Linux file system, not under /mnt/c. It's many times faster, and file watching (which Vite and tsx watch rely on) works properly there:
    commands
    $ mkdir -p ~/code && cd ~/code
  5. Install VS Code on Windows with the WSL extension. From any folder in the Ubuntu terminal, code . opens that folder in VS Code, connected to WSL. Files you see are the Linux files.
  6. For the headed browser tests, Windows 11 shows Linux windows on your desktop (this is WSLg). Install Edge for Playwright inside Ubuntu when you first need it: npx playwright install --with-deps msedge (it asks for your Linux password).
Windows

Run your AI agent inside WSL too (install its command-line tool in Ubuntu, or open the folder with code . and use the agent's VS Code extension, which then runs in WSL). If the agent runs on the Windows side, it will try PowerShell versions of the commands and the npm scripts will fail.

Your co-worker

Choose your agent

The course uses Codex, OpenAI's coding agent. Everything here also works with Claude Code (Anthropic) and Antigravity (Google's agent-first editor). Pick the one you already pay for. The ideas are the same; only the names of a few features differ.

What all three have in common:

  • They read an instructions file at the start of every chat: project rules, commands, things to avoid.
  • They can plan first: discuss and write a plan without touching files, until you approve.
  • They run terminal commands (with your permission) and edit files.
  • They can load skills: reusable instruction packs, such as the grilling skill this course uses.

Cost and safety

Cost and safety
  • Know how you're billed. A ChatGPT, Claude or Google subscription and an API key are billed separately. A coding agent on an API key can spend real money in an afternoon, because each step re-reads a lot of code.
  • Set usage alerts in the provider's billing page. Alerts warn you; they are not a hard stop. Check whether your provider also offers a spending limit and set it.
  • Never paste real keys or passwords into a prompt or into the repo. This project needs none: the payment service is a local mock and the databases use throwaway local passwords from docker-compose.yml.
  • Read before you approve commands. Approve npm test; think twice before approving anything that deletes outside the project folder or pushes to a remote.
  • Read-only for data. In Part 8 you'll let an agent look at traces. Give it read-only access; it never needs to change them.

Repo note: the README's port tables are wrong

The top-level README says Parts 5–8 get their own Redis, RabbitMQ and Jaeger on ports like 6305, 15606 and 16606. They don't. docker-compose.yml defines one of each, shared, on the ports above, and every part's package.json points at those. Trust the table on this page.

Careful: one RabbitMQ part at a time

Because RabbitMQ is shared, Parts 6, 7 and 8 all read the same auction.notifications queue. If two of them run at once, one part's worker can take the other part's messages, fail to find the matching row in its own database, and retry forever. Run one of Parts 6–8 at a time (stop it with Ctrl+C before starting another). Parts 1–5 can run side by side.

Stopping and resetting. Ctrl+C stops a part's processes; the containers keep running. npm run db:reset (inside a part) wipes and re-seeds only that part's database. docker compose down from the repo root stops the shared containers; add -v only if you want to delete every part's data.

Settings that matter

Agent basics: effort and usage

Effort (also called reasoning or thinking level) is how long the model thinks before it acts. More effort is slower and costs more, but catches more. Match it to the task:

TaskEffortExample from this course
A small, obvious editLowRename a label, fix a typo in a README
Everyday feature workMediumPart 2: post an auction form and its API route
Hard reasoning about time, order or failureHigh or extra highPart 3's race, Part 5's hidden defect, Part 6's crash-safe close
Reviewing someone else's changeHighPage 2's code review step
What the instructor does

The course is recorded on Medium effort to keep the videos moving. The instructor says that in his own work he prefers high or extra-high, and avoids "fast" modes that trade thinking for speed. Our suggestion: Medium for Parts 1–2, High from Part 3 onwards.

Usage. Agents show how much of your plan or budget you've used (Codex shows it in its status; Claude Code has a usage view; Antigravity shows model quota). Check it at the end of each part. If a single slice burns a surprising amount, the prompt was probably too vague and the agent wandered: tighten the prompt rather than raising the budget.

Warm-up

A throwaway first build

Before the real app, build something you'll throw away. The point is to feel how the agent works: how long it runs, what it asks, what it gets wrong. Use a scratch folder, not workshop:

commands
mkdir -p ~/code/practice && cd ~/code/practice && git init

The course also uses this step to name the tech stack. If you don't, the agent picks for you, and it may pick a framework you didn't want. Saying "React with Vite and TypeScript" up front costs one line.

Prompt to try Build

Start your agent in ~/code/practice (an empty folder). Effort: Medium.

Build a small auction website in this empty folder. It should look and feel like a
typical online auction site, for used computer hardware.

Tech stack (use exactly this, nothing extra):
- React + TypeScript, served by Vite
- No backend yet: keep the sample data in a TypeScript file
- No CSS framework, no component library, no router library

Pages (two routes only):
1. Home "/": a grid of 6 sample auctions. Each card shows a title, a current price
   in US dollars, the number of bids and the time left.
2. Auction "/items/<slug>": one auction with a larger picture area, the current
   price, time left, the seller's name and a bid box (the bid box does nothing yet).

Themes: offer three distinct visual themes (for example "classic", "dark",
"bold"). Put a theme switcher on the home page; the chosen theme applies to both
pages and survives a reload.

Before you write code, tell me in 5 lines or fewer how you will structure the files.
Then build it. When you're done:
- run the TypeScript type check and fix every error,
- start the dev server and tell me the exact URL,
- list what you did NOT build that a real auction site would need.
Why this prompt works
  • It names the stack and forbids extras, so you don't get a surprise UI library or a router you didn't ask for.
  • It defines "done" as checks the agent must run (type check, server up), not "looks finished".
  • Asking for the file plan first gives you one cheap moment to say "no" before it writes 20 files.
  • The last line ("what you did NOT build") makes the agent state its own gaps instead of hiding them.
If the agent goes off track, steer with
Stop. You added <THING I DIDN'T ASK FOR>. Remove it and keep to the stack I listed.
Then show me the file list again and re-run the type check.

What you should see

  • a home page with six cards and a theme switcher with three choices;
  • clicking a card opens /items/<slug>;
  • the theme sticks after a reload;
  • a short "not built" list (accounts, real bidding, payments…).
How it compares with the repo

The repo's part-1-foundation/web is what the author kept from this warm-up: a single-theme catalogue of six data-centre parts (an H100 GPU, an EPYC CPU, memory, a chassis, a switch, a cooling loop) with search and an item page. The theme switcher was practice and didn't survive. Throwing work away is normal; the agent made it cheap.

Install the grilling skills

While the build runs, install the course author's skills in a second terminal. A skill is a folder of instructions the agent can load on demand: here, how to interview you ("grill" you) before building, and how to write the answers into docs.

commands
cd ~/code/workshop
npx skills@latest add schneidenbach/skills

When it asks, pick these four: domain-modeling, grill-me, grill-with-docs, grilling, and choose your agent (Codex, Claude Code or Antigravity) as the target.

What each one is for (one line each):

  • grill-me: the agent asks you questions until the requirement is clear, then summarises.
  • grill-with-docs: the same, but it also writes the decisions into files (GRILL.md, and a glossary CONTEXT.md and decision records in later parts). This is the one the course uses every time.
  • grilling: shared rules the two grill skills follow (how many questions, how to recommend an answer).

The behaviour you need is simple: "Before building, ask me up to 10 questions per round, each with your recommended answer; at most 2 rounds; write the decisions to GRILL.md; then propose 2–4 slices and wait."

Checkpoint 0 / 4

Verification

Let the agent check its own work

An agent that says "done" hasn't proved anything. The cheapest proof for a web page is a browser: open it, click, look. The agent can do that itself with Playwright, which drives a real browser from code. Ask for a headed browser (a visible window) so you can watch it click; headless runs are fine later for the agent's own quick checks.

Prompt to try Test

Same chat, practice folder, dev server running. Effort: Medium.

Check the running practice site in a real, visible browser.

Use Playwright with Microsoft Edge (or Google Chrome if Edge isn't installed),
headed, not headless. If you can't open a visible window here, tell me and stop;
don't silently switch to headless.

Check these three things and give me PASS or FAIL for each, with the evidence
(what you clicked, what text you saw):
1. The home page shows exactly 6 auction cards.
2. Clicking the first card opens its /items/<slug> page with the same title and price.
3. Each of the three themes can be selected, changes the look, and is still
   selected after a page reload.

Leave the browser window open at the end so I can look. Put any screenshots in a
temporary folder outside this project. Don't change any source files in this step.
Why this prompt works
  • "PASS or FAIL with evidence" turns a vague "looks good" into something you can check.
  • Forbidding a silent switch to headless matters: some agents fall back without saying so, and then claim they "saw" the page.
  • "Don't change any source files" keeps checking and fixing as separate steps, so a test can't quietly be bent to pass.

What you should see: a visible Edge window clicking through your site, and a 3-row PASS/FAIL table in the chat. If anything fails, then ask for a fix in a separate message.

Windows

In WSL, the Edge window appears on your Windows desktop through WSLg. If Playwright says Edge isn't installed, run npx playwright install --with-deps msedge in Ubuntu and try again.

Teach the agent your project

Write AGENTS.md

AGENTS.md is a plain Markdown file in the project that the agent reads at the start of every chat. It's where you put what the agent can't guess: the real commands, the rules you care about, and how to check work. Claude Code reads CLAUDE.md (put @AGENTS.md in it to reuse the same file); Antigravity uses rules (point one at AGENTS.md).

Prompt to try Docs

Same practice folder. Effort: Medium.

Write an AGENTS.md for this project, for future AI agents working here.

First read the project (package.json, the folder layout, the config files) so you
only state what is true. Then write a short file, under 40 lines, with:
- the stack and the conventions to keep (and what not to add),

app.ts · lines 14–22
  app.get('/api/health', async (request, reply) => {
    try {
      await pool.query('SELECT 1');
      return { ok: true, db: 'ok', requestId: request.id };
    } catch (error) {
      request.log.error({ err: error }, 'database health check failed');
      return reply.code(503).send({ ok: false, db: 'down', requestId: request.id });
    }
  });
  1. 14 The route is registered on the Fastify app built in buildApp(). Building the app in a function (instead of starting a server at import time) lets the test call it with app.inject without opening a port.
  2. 16 SELECT 1 is the cheapest possible query. If it returns, the connection, the credentials and the database all work.
  3. 17 The body echoes request.id, which Fastify takes from the incoming x-request-id header (or generates as req-1, req-2…). An onRequest hook (lines 10–12) also puts it in the response header.
  4. 18–20 Any failure is logged with the error and answered with 503 Service Unavailable: "I'm up, but a dependency isn't." That's the right code for a health check, so a load balancer can stop sending traffic.

The habit that matters most

Plan before you build: grilling

Here is the most useful idea in the course. Before the agent writes any feature code, it interviews you. It reads the repo, then asks questions about the parts of your request that are unclear, each with a recommended answer. You reply. The decisions are written into a file (GRILL.md). Then it proposes the work as small slices and waits for your approval.

Why bother? Because the expensive mistakes aren't typos; they're misunderstandings. "Let people bid" hides a dozen choices: Who are "people" without a login? How is money stored? How much higher must a bid be? Who enforces it, the page or the server? What happens to bids after the deadline? If you don't decide, the agent decides silently, and you find out three slices later.

Grilling also leaves a record. A fresh chat, a teammate, or a second agent can read GRILL.md and know what was agreed, without the conversation.

Simulator

Grill-me demo

Try it. You're starting Part 2. The agent has read the repo and asks four questions. Pick an answer; try a 'wrong' one to see the agent push back.

How long to grill

The course limits grilling to two rounds of up to 8–10 questions, to keep the videos short. The instructor says that in real work he keeps going until nothing is unclear. A good rule: stop when the agent's questions start being about things you genuinely don't care about, and say so ("use your recommendation for the rest").

Key lesson

Rules that protect the business, such as "a seller can't bid on their own auction" or "a bid must be at least $1 higher", belong in the API, not only in the page. Anyone can send a request to the API without using your form. The page may show the rule; the server must enforce it.

Quiz

Check yourself

1 Where must the rule "a seller can't bid on their own auction" be enforced?

Anyone can send a request straight to the API without your page. The page can hint; only the server can enforce. (In Part 3, the check moves inside the database transaction.)

2 Which of these belongs in AGENTS.md?

AGENTS.md is for facts the agent can't guess and would otherwise get wrong. Generic advice adds nothing, file lists go stale, and secrets never go in the repo.

3 Why does the workshop copy start with rm -rf .git and empty Part 2–8 folders?

You're practising steering an agent. If the answers are in the folder or the history, the agent will find them and you'll learn nothing about planning or review.

4 On Windows, why does this course use WSL2 instead of PowerShell?

Scripts like API_PORT=3101 npm run dev and ../scripts/workshop-db assume a Unix shell. WSL2 gives you one, and Docker Desktop's WSL engine runs the containers.

5 Part 1's health route returns 503 when PostgreSQL is down. Why 503 and not 500?

A 500 says "I have a bug". A 503 says "I'm temporarily unable", so traffic can be routed elsewhere until the database is back.

6 In a grilling session, the agent asks "How should money be stored?" and recommends integer cents. What's the best reply if you don't have a strong view?

Recommendations exist so you can move quickly on things you don't care about. The decision still gets written down, so it's explicit, not silent.
