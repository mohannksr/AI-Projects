The heart of this page

The bidding-war bug

Every test passes. Every rule is enforced. And the auction is still broken.

The flaw in one line

Read the current price, check the bid, insert it: three steps that two requests can run at the same time, so both read $101 and both insert $102.

Each request is correct on its own. Ben's request reads $101, sees that $102 is at least $1 more, and saves it. Chen's request does exactly the same, a few milliseconds later, against the same $101, because Ben's bid isn't saved yet when Chen's request reads the price. Two accepted $102 bids. Both see "you are the highest bidder".

This is a race condition: the result depends on the timing of things running at once. Ordinary tests miss it because they send one request, wait for the answer, then send the next. Real users don't wait for each other, especially in the last seconds of an auction.

2Decisions you agree in the grilling

Question Decision Why it matters
How are bids for one auction decided?One at a time. A short PostgreSQL transaction locks the auction's row first (SELECT … FOR UPDATE).Two bids on the same auction can't interleave; bids on different auctions don't block each other.
When is the price read?After taking the lock. Re-read the highest bid inside the transaction.Reading before the lock is how the race happened.
If $103 and $106 arrive together on a $102 price?Requests are serialized, not batched. $106 always ends up leading. $103 is kept only if it got the lock first and was valid then.Simple to explain and test; no "auction batching" logic.
Which clock decides "closed"?The application clock, injected into the API so tests can set the time. Read after the lock.A bid that waited for the lock past 6:00 pm is judged at the moment of decision, not arrival.
What time is stored on the bid?The same clock reading used for the decision.The bid's timestamp and the closing check can't disagree.
What does a conflict look like?HTTP 409 with a stable code (BID_TOO_LOW, AUCTION_CLOSED, SELLER_CANNOT_BID), a readable error, and fresh currentPriceCents, minimumBidCents, endsAt.The page can react by code, not by parsing English.
What does the page do after a conflict?Refresh the whole auction, keep the typed amount, never resubmit. Retry the refresh if it fails; never retry the bid.The bidder decides what to do next. Money is never spent automatically.
How does an open page know it ended?Schedule a local switch to "Ended" at endsAt; recheck when the tab becomes visible again. No polling. The API stays authoritative.Background tabs pause timers, so the visibility recheck matters.
Idempotency keys for bid requests?Out of scope.Keeps the design small. Written down so it's a choice, not an oversight.
How is it verified?Deterministic concurrency tests in the API, clock-boundary tests, page tests for conflicts and the timer, and the bidding-war test flipped to demand protection.Same test, opposite assertion: it now proves the bug is gone.

Side explainer

Transactions vs locks

A common belief: "just wrap it in a transaction". A transaction makes a group of statements all-or-nothing. It does not, by itself, stop two transactions reading the same old value. Here's our race under four setups:

Setup What Ben and Chen read Result
No transaction (Part 2)Both read $101✗ Two accepted $102 bids
Transaction, default isolation (Read Committed), no lockBoth read $101: neither sees the other's uncommitted insert✗ Still two $102 bids
Read Committed + SELECT … FOR UPDATE on the auction row (Part 3)Ben reads $101. Chen waits for the lock, then reads $102, because each statement sees what was committed before it started✓ Chen rejected, minimum $103
Repeatable Read + FOR UPDATEChen waits, gets the lock, but its reads use a snapshot from the start of its transaction, so it may still see $101✗ Can still duplicate: this design relies on Read Committed

PostgreSQL's default is Read Committed, which is what the course code uses. The strictest level, Serializable, would instead abort one of the two transactions with a "could not serialize" error, and the API would have to retry it. The row lock is simpler: requests queue per auction and nobody needs a retry.

Our analysis

The Repeatable Read row is our own reasoning about PostgreSQL's rules, not something shown in the course. Ask your agent to prove or disprove it with a test: it makes a good review exercise.

Live updates with Socket.IO and Redis

Goal When Chen bids, Asha's and Ben's open pages update within a second, without a reload, even with several API servers.

Folder part-4-realtime-socketio-redisWeb :5104 · API :3104 · Redis :56379≈ 28 min of video

Until now, a page only learns about new bids when you reload it. In the last seconds of an auction that's useless. Part 4 makes pages live.

Two new pieces:

  • Socket.IO: a library that keeps an open connection between each browser and the API (a WebSocket), so the server can push messages without the browser asking.
  • Redis: a fast in-memory data store. Here it's used only as a backplane: if you run two or three copies of the API behind a load balancer, a bid handled by API copy 1 must reach a browser connected to API copy 2. Each copy publishes events to Redis and hears everyone else's.

The design choice that makes this simple: the live event carries no price. It just says "auction used-gpu changed". Each page then re-fetches the auction over normal HTTP. The database stays the only source of truth, and a missed or duplicated event can't put a wrong number on screen.

export function watchAuctionChanges(
  slug: string,
  onChanged: (event: AuctionChangedEvent) => void,
): () => void {
  const socket = io({ autoConnect: false, transports: ['websocket'] });
  socket.on('connect', () => {
    socket.emit('auction:watch', { slug }, (_result: SubscriptionResult) => undefined);
  });
  socket.on('auction:changed', (event: AuctionChangedEvent) => {
    if (event.slug === slug) onChanged(event);
  });
  const connectTimer = window.setTimeout(() => socket.connect(), 0);
  return () => {
    window.clearTimeout(connectTimer);
    socket.disconnect();
  };
}

Quiz

1 Part 2's tests all passed, but two $102 bids were accepted. Why did the tests miss it?

A race needs overlap. Sequential tests can't produce it; the bidding war (with a delay that widens the window) can.

2 In Part 3's fix, why must the current price be read after SELECT … FOR UPDATE?

The lock only helps if the decision uses data read while holding it. A price read before the lock is already stale for anyone who had to wait.

3 Chen's request arrives at 5:59:59.9 but waits 1 second for the lock. What does Part 3 do, and why?

The decision time is when the bid is actually judged, which is after the lock. The same reading is stored as the bid's time, so they can't disagree.

4 At the end of Part 2, the bidding-war test passes. What does that tell you?

Always read what a test asserts. In Part 2 it proves the bug exists; in Part 3 the same scenario is flipped to prove it's gone.

5 Why does Part 4 publish auction:changed only after COMMIT?

Before COMMIT, the bid isn't visible to other connections and might still be rolled back. Publishing early can make pages re-fetch the old state, or announce a bid that never happened.

6 Why does the Part 4 event carry only { slug, bidId } and no price?

The event is a doorbell. Whatever happens to the doorbell, the page ends up showing what the database says.
