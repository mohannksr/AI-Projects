Part 6

Close the auction and tell the winner, crash-proof

Goal Within seconds of 6:00 pm, the system records that Chen won with $107, and Dana and Chen each see one pop-up, even if a process crashes at any point.

Folder part-6-async-close-rabbitmqWeb :5106 · API :3106 · Redis :56379 · RabbitMQ :56726 (UI :15676)≈ 26 min of video

So far the deadline only stops new bids. Nothing happens at 6:00 pm. Part 6 adds the workflow a real auction site needs: record the outcome, then tell the people involved.

The design splits this into two background programs (called workers) so each has one job:

  • The close worker polls the database every second for auctions past their deadline, and records each one's outcome: the winning bid, or "no bids".
  • The notification worker tells the seller and the winner, with a pop-up in any browser tab they have open.

They're connected by RabbitMQ, a message broker: a program that holds messages in queues until a consumer takes and acknowledges them. The close worker publishes an AuctionClosed event; the notification worker consumes it.

The hard part is failure. What if the close worker records the close and crashes before publishing? The notification is lost. What if it publishes and crashes before noting that it did? It publishes again on restart, and Chen gets two pop-ups. Three ideas solve this, and the simulator below lets you crash each step:

  • Transactional outbox. Write the close and the event (into an outbox_events table) in one database transaction. Then publish from that table, marking each row published only after RabbitMQ confirms. A crash can delay a message; it can't lose one.
  • At-least-once delivery. The broker and the outbox may deliver a message more than once, never zero times.
  • Idempotency. Every step is safe to repeat: one close per auction, one outbox row per close, one delivery per (event, person), and a notification ID the browser remembers.

Working like a team

Issues, goals, worktrees and pull requests

Up to now you've driven the agent message by message. Real teams work from an issue tracker: a list of problems and requests, each with an owner. The course shows how to hand an agent a whole issue and let it run: it reads the issue, investigates, and opens a pull request (PR) for you to review, working on its own branch in a separate folder.

Two kinds of issue

A questionIssue #2: "Should we use an ORM instead of raw SQL?" → the deliverable is a written recommendation: an ADR (architecture decision record: a short file saying what was decided, why, and what was rejected).
A changeIssue #3: "Move Part 6's data access to Drizzle" → the deliverable is code: a PR on its own branch, reviewed before merging.

(Drizzle is a TypeScript ORM. An ORM maps tables to objects so you write less SQL by hand. Part 1 chose plain SQL deliberately; the issue asks whether that still holds.)

Worktrees. A git worktree is a second working folder for the same repo, checked out on a different branch. The agent can work in it while your main folder stays untouched:

commands
cd ~/code/workshop
git worktree add ../workshop-orm -b issue-2-orm-question
git worktree add ../workshop-drizzle -b issue-3-drizzle-part-6

Remove one when you're done: git worktree remove ../workshop-orm.

A worktree separates files, not infrastructure

Each worktree has its own files and branch, but they all share your PostgreSQL databases, ports, Redis and RabbitMQ. Two worktrees running Part 6 at once fight over port 3106, auction_part_6 and the queue. Run one demo at a time, or give the experiment its own database name and ports.

Goals. Codex has a goal feature for long tasks: you give one broad objective with success criteria, and it works through it with fewer check-ins. The instructor's advice: goals work best with a broad task, clear success criteria, and an issue tracker it can read and update. In other agents, the same thing is just a well-formed long prompt.

Winner checkout with a mock Stripe

Goal Chen, and only Chen, pays exactly $107, and the purchase is marked paid only when a signed message from the payment provider says so.

Folder part-7-winner-checkoutWeb :5107 · API :3107 · Mock Stripe :7107≈ 13 min of video

Stripe is a payment provider. In hosted checkout, your server asks Stripe for a checkout session (with the amount), sends the buyer to Stripe's own payment page, and later receives a webhook: an HTTP request from Stripe to your server saying "this session was paid". The repo includes stripe-service/, a small local service shaped like Stripe, so no real account or card is involved.

The one rule that matters: the browser's word is never proof of payment. After paying, the buyer's browser is redirected back to your site with something like ?checkout=success in the URL. Anyone can type that. Only the webhook, signed with a secret shared between the provider and your server, counts.

export function verifyStripeSignature(body: Buffer, signature: string, secret: string): boolean {
  const expected = createHmac('sha256', secret).update(body).digest();
  let supplied: Buffer;
  try {
    supplied = Buffer.from(signature, 'hex');
  } catch {
    return false;
  }
  return supplied.length === expected.length && timingSafeEqual(supplied, expected);
}
  1. 91 Recompute the HMAC (a keyed hash: only someone with the secret can produce it) over the raw body.
  2. 98 Compare with timingSafeEqual, which takes the same time whatever the input. An ordinary === stops at the first wrong character, and an attacker timing many requests could learn the signature byte by byte. The length check first is needed because timingSafeEqual throws on different lengths.

Why real Stripe adds a timestamp

The mock signs only the body. If someone captured one real webhook, they could send it again later, and the signature would still be valid. Here that replay is harmless, because the event ID is recorded and the purchase is already paid. Real Stripe goes further: its Stripe-Signature header includes a timestamp, the signature covers the timestamp plus the body, and its libraries reject events older than a few minutes. That limits replays even before your own deduplication runs.

Follow one auction across services with Jaeger

Goal Open one trace and see Chen's winning bid, the close, both messages, checkout and payment, across four services, with nothing noisy and nothing private.

Folder part-8-cross-stack-debuggingWeb :5108 · API :3108 · Mock Stripe :7108 · Jaeger UI :16686 · OTLP :4318≈ 19 min of video

By now one auction touches four programs (the API, the close worker, the notification worker and the mock Stripe), plus PostgreSQL, Redis and RabbitMQ. When Chen says "I paid but it still says pending", where do you look? Reading four sets of logs by timestamp is slow and error-prone. This part adds distributed tracing.

📜 LogsWhat one program said, line by line. Great for detail; hard to join across programs.
📈 MetricsNumbers over time: requests per second, error rate. Tell you that something is wrong.
🧭 TracesOne request's journey across programs, as a tree of timed steps. Tell you where.

Words:

  • A span is one timed operation (accept a bid, publish a message). Spans nest: a parent and its children.
  • A trace is all the spans for one piece of work, sharing a trace ID.
  • Context propagation is how the trace ID travels: in HTTP headers (the W3C traceparent header), in message headers, or, for work that happens much later, saved in a database row.
  • OpenTelemetry (OTel) is the standard library that records spans. Jaeger is a tool that stores them and shows them.

The interesting part of this design is the time gaps. Chen's bid happens at 5:59:58. The close happens at 6:00:01 in another process. Checkout happens minutes later, when Chen gets round to it. No request lasts that long, so the trace context can't simply ride along in memory. Part 8 stores the traceparent on the auction, close and outbox rows, carries it in RabbitMQ headers, and keeps it with the mock Stripe session, so all of it joins one trace without leaving any span open while the system waits.

export function contextFromTraceparent(traceparent?: string | null): Context {
  return traceparent ? propagation.extract(ROOT_CONTEXT, { traceparent }) : ROOT_CONTEXT;
}

export function contextFromHeaders(headers: Record<string, unknown>): Context {
  const traceparent = headers.traceparent;
  const tracestate = headers.tracestate;
  return propagation.extract(ROOT_CONTEXT, {
    ...(typeof traceparent === 'string' ? { traceparent } : {}),
    ...(typeof tracestate === 'string' ? { tracestate } : {}),
  });
}

export function traceHeaders(source: Context = context.active()): Record<string, string> {
  const carrier: Record<string, string> = {};
  propagation.inject(source, carrier);
  return carrier;
}

The method, in six lines

What to remember

  1. Plan. Let the agent grill you; write the decisions down. "Money in integer cents, the API enforces +$1."
  2. Slice. Two to four pieces, each ending in something you can click. Build one, stop, review. "Catalogue, then post, then bid."
  3. Prove the bug. Before fixing, make it visible and repeatable. "Four windows, two accepted $102 bids."
  4. Fix it. At the right layer, with the smallest change. "Lock the auction row, then read the price."
  5. Verify. Tests, type checks and a real browser, run by the agent, with the output shown. "The same bidding war, now demanding no duplicates."
  6. Review. A fresh pair of eyes, and evidence for every finding. "A smaller model found FOR SHARE by comparing GRILL.md with the code."

The agent wrote almost every line of this app. What made it work was everything around the code: the questions, the slices, the tests that proved things, and the reviews that didn't take "done" for an answer. Those habits carry over to any project and any agent.

Check yourself

Quiz

1 Part 5 changed FOR UPDATE to FOR SHARE. Why does that bring the race back?

A shared lock only blocks writers of that row. The bid transactions never write the auction row, so nothing makes them wait for each other.

2 Why does Part 6 write the close and an outbox_events row in the same transaction, instead of publishing to RabbitMQ right after committing?

The database and the broker can't commit together. The outbox makes "the close happened" and "the event must be sent" one atomic fact; publishing becomes a retryable step.

3 Why is ON CONFLICT (outbox_event_id, recipient_user_id) DO NOTHING enough to handle redelivered messages?

The database does the deduplication. Combined with "emit only unsent deliveries" and the browser remembering notification IDs, repeating any step is harmless.

4 After paying, Chen's browser returns to /items/used-gpu?checkout=success. Why doesn't the API mark the purchase paid on that?

Browsers are controlled by users. Redirects are navigation hints; proof comes server-to-server, signed.

5 In the Jaeger trace, which span is where work crosses from the close worker into another service through RabbitMQ?

The producer span injects traceparent into the message headers; the notification worker extracts it and starts auction.closed.consume.

6 In Part 8, a declined card is recorded as mock_stripe.payment.outcome=declined, not as an error span. Why?

If every rejected bid and declined card were an "error", real failures would drown in noise. Outcomes go in attributes; errors are for faults.
